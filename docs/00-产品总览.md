# 个人博客项目 · 需求总览

> 版本：v0.1（需求整理稿）  
> 日期：2026-11-10  
> 状态：待评审

## 1. 项目背景

不是单纯做一个"写文章的地方"，而是把博客扩展成**个人数字生活中枢**：

- 一边沉淀内容（博客文章、笔记）
- 一边用自建小工具提升创作与分发效率（公众号、小红书）
- 一边记录生活与成长（自己、孩子、家庭）

核心诉求是**数据自持、工具自用、长期可维护**，而不是做一个面向公众的 SaaS 产品。

## 2. 产品定位

| 项目 | 说明 |
|---|---|
| 用户 | 单人使用（自己），不考虑多租户、注册登录体系 |
| 形态 | 一个统一入口的 Web 应用，包含博客、工具集、工作台、资源库 |
| 部署 | 优先本地/自托管，数据可导出、可备份、可迁移 |
| 气质 | 安静、克制、效率优先，不做社交与增长功能 |

### 设计原则

1. **本地优先**：数据默认存在本地，云端能力（AI、图床）可选且可关闭。
2. **模块独立**：四大模块可单独使用，也可按需关闭，不互相绑架。
3. **先解决高频痛点**：优先做每天都在用的功能，不为"完整性"堆功能。
4. **产物可直接用**：导出的图片、HTML 无水印、无平台锁定。
5. **低维护成本**：一个人能长期运营，依赖少、升级简单。

## 4. 典型使用场景

1. **周末创作**：在博客里写完一篇 Markdown → 一键排版复制到公众号 → 同时导出 4 张长图发小红书。
2. **做封面**：用画布模板 3 分钟做一张小红书首图，换配色导出 2x PNG。
3. **日常积累**：浏览器里 40 个标签一键存为"工作集"，下周继续；书签自动按主题归类。
4. **生活记录**：手机端 30 秒记录一次跑步或孩子的一句话，月底自动生成回顾。
5. **年度回望**：从工作台生成年度总结草稿，脱敏后发布到博客。

## 5. 整体信息架构（建议）

```
首页 / 仪表盘
├── 文章（博客）
├── 工具箱
│   ├── 公众号排版
│   ├── 长图生成
│   └── 首图画布
├── 工作台
│   ├── 时间轴
│   ├── 健康 / 运动 / 饮食
│   ├── 孩子成长
│   └── 家庭规划
├── 资源库（网页整理 / 导航页）
└── 设置（数据备份、主题、AI 开关）
```

## 6. 技术架构初稿（待确认）

| 层 | 建议 | 说明 |
|---|---|---|
| 前端 | React / Next.js + TypeScript + Tailwind | 工具与工作台都是重交互，组件化收益大 |
| 编辑器 | TipTap 或纯 Markdown 编辑器 | 博客与排版工具可复用 |
| 画布 | Fabric.js / Konva | 图层、拖拽、导出成熟 |
| Markdown | unified / remark / rehype + Shiki | 解析与代码高亮 |
| 图片导出 | html-to-image 或 Satori + resvg | 长图、首图导出 |
| 数据 | SQLite（自托管）或 IndexedDB（纯本地） | 视部署方式决定 |
| 浏览器扩展 | Chrome MV3 | Safari 视成本后置 |
| 部署 | Docker（NAS/云服务器）/ Vercel + 本地服务 | 需确认是否需要公网访问 |
| AI | 可选 LLM，用于归类、摘要、模板生成 | 默认关闭，隐私可控 |

## 7. 迭代路线（建议）

| 阶段 | 内容 | 目标 |
|---|---|---|
| M0 基建 | 仓库结构、设计系统、导航壳、数据存储、备份导出 | 能跑起来、数据不丢 |
| M1 工具箱 MVP | 公众号 Markdown 排版 + Markdown 长图 | 覆盖最高频创作场景 |
| M2 首图画布 | 画布编辑器 + 模板 + PNG 导出 | 小红书封面可独立完成 |
| M3 工作台 MVP | 时间轴 + 运动 + 健康指标 + 孩子里程碑 + 月度回顾 | 开始持续记录 |
| M4 网页整理 | 浏览器扩展采集 + 聚类 + 搜索 + 工作集 + 导航页 | 解决信息杂乱 |
| M5 博客与联动 | 博客发布、资源页、年度总结自动草稿 | 形成闭环 |

> 排序理由：B 模块使用频率最高、见效最快；C 模块需要时间积累数据，应尽早开始；A 模块依赖扩展开发，成本较高；D 模块可复用现有博客框架，最后整合。

## 8. 成功标准

- 公众号排版从 15 分钟降到 2 分钟内，粘贴后样式基本不丢。
- 3 分钟内完成一张合格的小红书首图。
- 工作台记录一条 ≤ 30 秒，且能坚持每周使用。
- 任意收藏内容 30 秒内能搜到。
- 所有数据可一键导出，迁移不依赖本系统。

## 9. 风险与约束

| 风险 | 影响 | 应对 |
|---|---|---|
| 公众号 HTML/CSS 兼容性差 | 排版效果不稳定 | 只用内联样式，建立兼容白名单与回归样例 |
| 画布功能容易膨胀 | 工期失控 | 首版只做文字、图片、形状、背景、模板 |
| 工作台记录负担过重 | 用几天就弃用 | 轻记录、重回顾；默认字段最少化 |
| 浏览器扩展跨浏览器成本 | 覆盖不全 | 先 Chrome/Edge，Safari 后置 |
| 健康/家庭数据敏感 | 隐私风险 | 默认本地、加密备份、公开需显式脱敏 |
| 单人维护 | 长期停更 | 少依赖、少自定义、优先静态化 |

## 10. 待确认问题（关键决策）

1. **部署方式**：纯本地运行、NAS 自托管，还是需要公网可访问？是否需要域名与 HTTPS？
2. **多设备**：是否需要在手机端记录（健康、饮食、孩子）？是否需要多端同步？
3. **博客站点**：是否已有框架（Hexo / Hugo / Next.js / Notion）？本次是一起做，还是只做工具与工作台？
4. **浏览器范围**：扩展优先支持 Chrome、Edge 还是 Safari？
5. **AI 边界**：是否允许把标题/URL/文章内容发给云端模型做归类与摘要？
6. **公众号图片**：是否需要图床（自建或第三方）与自动压缩？
7. **首图能力**：首版只做单张编辑，还是需要批量套模板一次出多张？
8. **工作台粒度**：每天打卡式记录，还是事件式记录？饮食是否需要精细到卡路里？
9. **家庭协作**：是否需要伴侣/家人共同记录（涉及多用户与权限）？
10. **移动端形态**：PWA 即可，还是需要原生 App？
11. **提醒能力**：疫苗、体检、纪念日等是否需要提醒？通过什么渠道（站内/邮件/微信）？
12. **数据量级**：预计书签/历史记录规模（几百 / 几千 / 几万），决定存储与搜索方案。
